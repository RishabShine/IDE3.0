\section{Purpose of the Project}
\subsection{User Business}

As AI allows the generation of code to come much more cheaply, the engineering
intent that comes behind a software system, such as its rationale and its
functional and non-functional requirements, gets lost across the quick and messy
repetitive prompt, answer, and code generation cycle. Developer teams lose the
traceability between the intent and the code/tests, which ultimately hurts
maintainability and software scalability, because through the bloated system it
is hard to find justification for why the system is built the way it is and how
the loss of control over quality and acceptance came to be.

A tool is needed that can allow traditional software engineering practices and
principles to persist and be applicable through AI agentic code and test
generation that enforces and streamlines these principles.

\subsection{Goals of the Project}

The overarching goal of \progname{} is to provide tool support that keeps human
engineers in control of engineering intent and software quality within an
AI-native (SE3.0) development workflow, where engineers define the goals,
constraints, and acceptance criteria and AI agents operationalize them. This
overarching goal is refined into the following supporting goals:

\begin{itemize}
  \item[\textbf{G1}:] Enable a developer to capture the engineering intent
  behind a change from natural-language interaction with an AI coding assistant,
  and require explicit developer approval of that intent before any code is
  generated.
  \item[\textbf{G2}:] Maintain a versioned intent model which consists of the following: the software's
  requirements, quality constraints, and design rationale. This will be a durable artifact that may be in a read-only 
  setting for the user so requirement linage is not tampered with and it serves as a source of truth for the software application journey and evolution. 
  \item[\textbf{G3}:] Maintain traceability links from each element of the
  intent model to the code and tests that implement it, each with a recorded
  justification.
  \item[\textbf{G4}:] Verify changes proposed or generated by an AI coding
  assistant against the intent model, and report whether they satisfy the
  recorded requirements and constraints.
  \item[\textbf{G5}:] Keep the developer in control of the system's engineering
  intent, so that every change to the intent model is reviewed and approved by a
  human before it takes effect (always have a human-in-the-loop). 
\end{itemize}
\section{Stakeholders}
\subsection{Client}

\subsection{Customer}

The customers for \progname{} are software engineering development teams that
build and evolve software with the help of AI coding assistants. These teams
need to manage their requirements, quality constraints, and the evolution of
their application through code that is written and changed across multiple
developers. For these customers, engineering intent is easily lost as work is
spread across many contributors and there custom agentic systems, so they need a way
to keep engineering principles connected to the code and test cases that implement them. 
\progname{} is intended to serve these teams by keeping that intent explicit, traceable, and under human control.

\subsection{Hands-On Users of the Project}

\progname{} has three categories of hands-on users.

\begin{itemize}
  \item \textbf{AI-assisted developer.} Writes code with an AI coding assistant
  inside an IDE. Submits requests, reviews and approves proposed requirements,
  and reads verification results.
  \begin{itemize}
    \item Subject matter experience: knows the software being built.
    Familiar with requirements and design concepts, but may not write formal
    requirements.
    \item Technological experience: comfortable with an IDE, Git, and at least
    one AI coding assistant.
    \item Education: undergraduate degree in software engineering, computer
    science, or equivalent experience.
    \item Attitude toward technology: uses AI tools daily and wants to keep
    their speed. Will avoid steps that feel slow or repetitive.
  \end{itemize}

  \item \textbf{Technical lead or reviewer.} Reviews changes made by other
  developers. Uses the intent model, traceability links, and verification
  results to judge whether a change meets its requirements.
  \begin{itemize}
    \item Subject matter experience: high. Understands the system design and
    its quality priorities.
    \item Technological experience: high. Uses Git, GitHub pull requests, and
    code review tools.
    \item Attitude toward technology: values traceability and control over
    speed. Sceptical of AI-generated code.
  \end{itemize}

  \item \textbf{New team member.} Joins a project that already uses
  \progname{}. Reads the intent model to learn why the code is structured the
  way it is.
  \begin{itemize}
    \item Subject matter experience: low for the project being joined.
    \item Technological experience: comfortable with an IDE and Git.
    \item Attitude toward technology: relies on documentation and existing
    artifacts to learn the codebase.
  \end{itemize}
\end{itemize}

\section{Mandated Constraints}
\subsection{Solution Constraints}

\medskip
\noindent\textbf{Description:} The product shall integrate with and run inside
multiple integrated development environments (IDEs). VS Code and Cursor are the
primary targets, and PyCharm is a secondary target if time permits. \\
\textbf{Rationale:} Developers work in different IDEs, so the tool must meet them
in the environment they already use rather than forcing them to adopt a new one. \\
\textbf{Fit Criterion:} The core intent-capture and approval workflow shall be
verified to run inside VS Code and Cursor, and support for PyCharm shall be
attempted if the schedule allows.

\medskip
\noindent\textbf{Description:} The product shall function with multiple agentic
coding assistants. Claude Code is the primary target, and Codex and Grok or
Cursor AI are secondary targets if time permits. \\
\textbf{Rationale:} Teams rely on different AI coding assistants, and the tool
must capture intent and constrain generated code regardless of which assistant
produces it. \\
\textbf{Fit Criterion:} The product shall be verified to capture intent and gate
code generation when driven by Claude Code, and compatibility with Codex and
Grok or Cursor AI shall be attempted if the schedule allows.

\subsection{Implementation Environment of the Current System}

In the current design, \progname{} runs locally on the developer's machine as an
IDE extension together with the IDE terminal running a AI coding assistant or 
an IDE plugin tool. The extension and server coordinate through
files in the developer's workspace, and requirement extraction verification may call an
external large language model service over the network. The product shall
function on the operating systems that host the supported IDEs, namely Windows,
macOS, and Linux.

\progname{} is designed to work alongside the developer's existing AI coding
assistant and host IDE rather than replace them, and it integrates with the
project's version control system (Git and GitHub) to version the intent model.
These are the applications the product must cooperate with, and there are no
other partner or collaborative constraints at this time.

\section{Relevant Facts And Assumptions}
\subsection{Relevant Facts}

The following facts are outside the control of the project but shape its
requirements.

\medskip
\noindent\textbf{RF1.} Some AI coding assistants offer their own ways to carry
context between sessions, such as memory files or project rules. This context
is specific to each tool, unstructured, not versioned, and not reviewed. It does
not record requirements, design decisions, or their rationale in a form that can
be traced or reused by a different assistant.

\medskip
\noindent\textbf{RF2.} AI coding assistants can generate code directly from an
informal natural-language prompt. Nothing in this workflow requires the
developer to state requirements, architecture, or interfaces before code is
generated.

\medskip
\noindent\textbf{RF3.} Established languages for writing formal contracts
already exist. Examples include the Java Modeling Language (JML) for Java, and
libraries such as icontract and deal for Python. Tools such as OpenJML can check
JML contracts against Java code.

\medskip
\noindent\textbf{RF4.} VS Code provides a public extension API, and existing
extensions already support UML modelling and visualization inside the IDE.

\medskip
\noindent\textbf{RF5.} LLM output is not deterministic. The same request can
produce different requirements, designs, or code on different runs, so
generated artifacts cannot be trusted without human review.

\subsection{Business Rules}

The following rules describe how the intent refinement process must be carried
out. They apply regardless of how the product is implemented.

\medskip
\noindent\textbf{BR1.} Intent is refined in ordered stages: high-level intent,
epics and requirements, architecture, module and interface specifications,
formal contracts, and code generation.

\medskip
\noindent\textbf{BR2.} The artifacts produced at each stage must be reviewed and
approved by the developer before the process moves to the next stage. The
developer may also edit or reject them.

\medskip
\noindent\textbf{BR3.} The developer may return to any earlier stage when
requirements or designs change. Artifacts in later stages that depend on the
changed artifacts must then be reviewed again.

\medskip
\noindent\textbf{BR4.} Code is generated only from approved specifications and
contracts, never directly from the developer's initial request.

\medskip
\noindent\textbf{BR5.} Only a human developer can approve, edit, or reject an
artifact. The AI may propose and refine artifacts but cannot approve them.

\medskip
\noindent\textbf{BR6.} An experienced developer may enter technical constraints,
interfaces, or contracts directly at any stage instead of describing them in
natural language.

\medskip
\noindent\textbf{BR7.} Every approved artifact must be traceable to the
artifact in the previous stage that it refines, back to the original
high-level intent.

\subsection{Assumptions}

The following assumptions were made to keep the project feasible within the
capstone timeline. If any of them turns out to be false, the affected
requirements will need to be revised.

\medskip
\noindent\textbf{AS1.} The initial implementation focuses on intent capture and
refinement (Feature Group A). Post-generation traceability, explanation, and
verification (Feature Group B) are documented as requirements but are treated
as future work.

\medskip
\noindent\textbf{AS2.} The product reuses existing contract languages and
verification tools to enforce or check contracts. It does not include a custom
system for proving that generated code meets its specifications.

\medskip
\noindent\textbf{AS3.} The refinement process is designed to be independent of
programming language and coding agent. The stages from high-level intent to
interface specifications do not depend on the language. Contract generation and
checking are language-specific, so they will be supported for a limited set of
languages chosen based on the case study. Support for additional languages can
be added through separate contract and verification adapters.

\medskip
\noindent\textbf{AS4.} The product is used by a single developer working in a
local workspace. Multi-user collaboration on the same intent model is not
supported in the initial implementation.

\medskip
\noindent\textbf{AS5.} The developer has a supported IDE installed, such as VS
Code, and has access to an LLM service and an AI coding assistant.

\medskip
\noindent\textbf{AS6.} The developer has enough software engineering knowledge
to review requirements, architectural decisions, interface specifications, and
contracts.

\medskip
\noindent\textbf{AS7.} The proof of concept will be demonstrated and evaluated
on a single case study of manageable size, such as an existing academic or
co-op project.

\medskip
\noindent\textbf{AS8.} The workflow may be simplified where necessary, for
example by merging or skipping stages for small requests, provided that human
approval is kept before code generation.

\section{The Scope of the Work}
\subsection{The Current Situation}
The current situation of the system is that the codebase a developer produces
comes out of a shallow, multi-turn conversation with the coding assistant, where
the developer provides it with a large amount of context about what the system
should be able to achieve and the coding assistant uses whatever knowledge it
has and generates the code. This code is generated without any traceable intent,
without the strict engineering principles that evolve and grow the idea, and
without the code-based contracts that should be expected when handling large
software systems. Figure~\ref{fig:current} summarises this workflow and the
stages that are absent from it today.

\subsection{The Context of the Work}
The work here is to follow the V-model in software-based application engineering
(illustrated in Figure~\ref{fig:vmodel}). The user uses the tool
to be guided toward making decisions that are driven by stronger and
well-established engineering principles. They are guided to take their
high-level overview requirements or wants for the system and go through a
journey of decomposition into more granular requirements in every domain that is
identified (functional, non-functional, quality, design, and so on).
The granular, feasible, executable requirements that are produced from the
approval and rejection decisions of the human in the loop then direct the coding
agent to generate contract-bound code. Contracts and interfaces are built so
that the code cannot violate the requirements. Finally, a validation and
verification phase checks the generated code against the user-developed and
agent-assisted intent model and its contracts.

Figure~\ref{fig:context} shows the context of the work as the named flows it
exchanges with the adjacent systems it depends on.

\subsection{Specifying a Business Use Case (BUC)}

\medskip
\noindent\textbf{BUC name:} Capture and approve the requirements for a feature.

\medskip
\noindent\textbf{Triggering event:} A developer submits a natural-language
feature request to the AI coding assistant. 

\medskip
\noindent\textbf{Actors:} The developer initiates the request and makes the approval decision. The AI coding assistant
extracts the candidate requirements. The intent model database stores the approved result.

\medskip
\noindent\textbf{Precondition:} The developer is working inside a supported IDE
with \progname{} active. No proposal is currently pending for the same request.

\medskip
\noindent\textbf{Postcondition:} A versioned set of approved requirements and
constraints is recorded in the intent model. Code generation for the request is
unblocked for exactly those requirements.

\medskip
\noindent\textbf{Main scenario:}
\begin{enumerate}
  \item The developer describes the desired feature in natural language.
  \item The work extracts a structured set of candidate functional,
  non-functional, quality, and design requirements from the request. The work
  saves them as a draft proposal.
  \item The work presents the proposal to the developer for review. No code is
  generated while the proposal is pending.
  \item The developer edits, removes, or adds requirements until the proposal
  reflects the intended behaviour.
  \item The developer approves the proposal.
  \item The work records the approved requirements, their rationale, and the
  originating request in the versioned intent model. The work then signals the
  AI coding assistant that generation may proceed for exactly those
  requirements.
\end{enumerate}

\medskip
\noindent\textbf{Alternative (rejection):} At step~5 the developer may reject
the proposal instead of approving it. The work then discards the draft and keeps
generation blocked. It asks the developer to revise the request and returns to
step~1.

\section{Business Data Model and Data Dictionary}
\subsection{Business Data Model}

The business data model for \progname{} represents the engineering intent of a
software project and the relationships between that intent and its implementation.

The primary entities in the model are:

\begin{itemize}
    \item \textbf{Project:} Represents the software project being developed and
    contains the engineering artifacts and traceability information maintained by
    \progname{}.

    \item \textbf{Developer Request:} Represents information provided by an
    engineer describing a desired change, feature, constraint, or other engineering
    intent. A request may result in the creation or refinement of multiple
    engineering artifacts.

    \item \textbf{Engineering Artifact:} Represents a piece of engineering intent
    associated with the project. Engineering artifacts may include requirements,
    constraints, design decisions, and implementation contracts.

    \item \textbf{Artifact Relationship:} Represents a relationship between two
    engineering artifacts, such as a dependency, refinement, constraint, or
    conflict.

    \item \textbf{Implementation Artifact:} Represents an element of the developed
    software, such as a source file, class, method, or test.

    \item \textbf{Traceability Link:} Connects an engineering artifact to an
    implementation artifact and records the relationship between the engineering
    intent and its implementation.
\end{itemize}

A project may contain many developer requests and engineering artifacts. A
developer request may produce or refine multiple engineering artifacts, and an
engineering artifact may be related to other artifacts through artifact
relationships. Engineering artifacts may also be connected to one or more
implementation artifacts through traceability links.

\section{The Scope of the Product}
\subsection{Product Boundary}

\progname{} is a software engineering support tool that assists engineers in
refining engineering intent into precise artifacts that can be used to guide
AI headed implementation. The product accepts engineering information at
varying levels of detail, ranging from broad natural language descriptions to
more structured artifacts such as requirements, models, constraints, and formal
Specifications (e.g. UML, JML, …).

The product is responsible for interpreting this information, identifying
ambiguity or missing detail, and interacting with the engineer to progressively
refine the engineering intent. This process continues until sufficiently precise
artifacts, such as implementation contracts, preconditions, postconditions, and
other constraints can be produced. \progname{} also manages the persistence,
relationships, rationale, and traceability of these engineering artifacts as the
project evolves.

The generation and modification of application code are outside the product
boundary and are performed by an external coding agent using the engineering
artifacts produced by \progname{}. The host IDE, external AI models, version
control systems, and the software application being developed are also external
systems that \progname{} may interact with but does not implement.

\subsection{Individual Product Use Cases (PUC's)}

\noindent\textbf{PUC1: Provide Engineering Intent}\\
\textbf{Trigger:} The engineer begins a new development request.\\
\textbf{Pre-condition:} The engineer has a software project open in a supported development environment.\\
\textbf{Outcome:}
\begin{enumerate}
    \item The engineer provides engineering intent to the system.
    \item The input may range from broad natural language descriptions to structured engineering artifacts.
    \item The system interprets the provided information and identifies candidate requirements, constraints, design decisions, or other engineering artifacts.
\end{enumerate}

\noindent\textbf{PUC2: Refine Engineering Intent}\\
\textbf{Trigger:} The system determines that the provided engineering intent is ambiguous, incomplete, or insufficiently detailed.\\
\textbf{Pre-condition:} Engineering intent has been provided to the system.\\
\textbf{Outcome:}
\begin{enumerate}
    \item The system identifies information that requires further clarification or specification.
    \item The system requests additional information from the engineer.
    \item The engineer provides further details.
    \item The system updates and refines the corresponding engineering artifacts.
    \item This interaction may continue until the system deems that sufficient detail has been provided.
\end{enumerate}

\noindent\textbf{PUC3: Review and Approve, Reject, or Revise Engineering Artifacts}\\
\textbf{Trigger:} The system produces proposed engineering artifacts for review.\\
\textbf{Pre-condition:} One or more proposed engineering artifacts have been derived or refined.\\
\textbf{Outcome:}
\begin{enumerate}
    \item The system presents the proposed engineering artifacts to the engineer.
    \item The engineer reviews the proposed artifacts.
    \item The engineer may approve, reject, or revise individual artifacts.
    \item Approved artifacts are accepted into the project's engineering intent model.
    \item Rejected or revised artifacts may return to the refinement process.
\end{enumerate}

\noindent\textbf{PUC4: Generate Implementation Contracts}\\
\textbf{Trigger:} The engineering intent has been refined to a sufficient level of detail.\\
\textbf{Pre-condition:} The relevant engineering artifacts have been reviewed and approved by the engineer.\\
\textbf{Outcome:}
\begin{enumerate}
    \item The system derives precise implementation contracts from the approved engineering artifacts.
    \item Contracts may include preconditions, postconditions, invariants, or other implementation constraints.
    \item The system associates the generated contracts with the engineering artifacts from which they were derived.
    \item The engineer is able to review the resulting contracts before implementation.
\end{enumerate}

\noindent\textbf{PUC5: Resolve Conflicting or Ambiguous Engineering Intent}\\
\textbf{Trigger:} The system identifies a potential conflict, inconsistency, or ambiguity between engineering artifacts.\\
\textbf{Pre-condition:} Existing engineering artifacts are available in the project model.\\
\textbf{Outcome:}
\begin{enumerate}
    \item The system identifies the artifacts involved in the conflict or ambiguity.
    \item The system presents the issue and relevant context to the engineer.
    \item The engineer provides clarification or selects the intended interpretation.
    \item The system updates the affected engineering artifacts and relationships.
\end{enumerate}

\noindent\textbf{PUC6: Send Approved Engineering Context to Coding Agent}\\
\textbf{Trigger:} The engineer approves the engineering artifacts and implementation contracts for a development task.\\
\textbf{Pre-condition:} Sufficient engineering intent and implementation contracts have been approved.\\
\textbf{Outcome:}
\begin{enumerate}
    \item The system collects the approved contracts and relevant engineering context.
    \item The system provides this information to the external coding agent.
    \item The coding agent uses the provided engineering context to perform the requested implementation.
\end{enumerate}

\noindent\textbf{PUC7: Trace Engineering Intent to Implementation}\\
\textbf{Trigger:} The engineer selects an engineering artifact and requests its implementation traceability.\\
\textbf{Pre-condition:} The selected engineering artifact has an established traceability relationship with implementation artifacts.\\
\textbf{Outcome:}
\begin{enumerate}
    \item The system retrieves the traceability relationships associated with the selected engineering artifact.
    \item The system identifies the relevant source code, tests, or other implementation artifacts.
    \item The system presents the relationships and available justification to the engineer.
\end{enumerate}

\noindent\textbf{PUC8: Trace Implementation to Engineering Intent}\\
\textbf{Trigger:} The engineer selects an implementation artifact and requests information explaining its engineering intent.\\
\textbf{Pre-condition:} The selected implementation artifact has an established traceability relationship with engineering artifacts.\\
\textbf{Outcome:}
\begin{enumerate}
    \item The system retrieves the engineering artifacts associated with the selected implementation artifact.
    \item The system presents the related requirements, constraints, contracts, or design decisions.
    \item The system presents available rationale or justification explaining why the implementation exists.
\end{enumerate}

\medskip
\noindent\textbf{IR3 (Isolation).} The system shall isolate concurrent
operations on the intent model so that they do not interfere
with one another. 

\medskip
\noindent\textbf{IR4 (Durability).} The system shall ensure that once a change is
committed it is persisted durably.
Committed intent(s) shall be versioned so that the state of the intent
model can be recovered and its history reviewed so that nothing is silently lost or unrecoverable.
