\section{General Information}

\subsection{Summary}

% \wss{Say what software is being tested.  Give its name and a brief overview of
%   its general functions.}

The software under test is IDE3.0, a VS Code extension that assists developers
in turning a high-level goal into explicit, reviewable requirements, and keeps
those requirements binding on any AI coding assistant that can implement them.
Without such a tool, the developer struggles with the traceability and
maintainability of goals and constraints since, during development, those
details live only in the chat and prompt phase and are lost when the session
is completed. IDE3.0 instead takes a new spec-driven development approach in
which the important details are treated as artifacts that are versioned in an
intent model, with elicitation artifacts, requirements, rationale, and trace
links that live within the project's repo.

The elicitation follows a staged and structured pipeline, the first stage of
which is the goal decomposition that proposes impacts, deliverables,
and user stories from the developer's goals. A clarification step then asks
about missing rules, exceptions, constraints, and quality needs rather than
the coding assistant inventing them. Finally, a specification stage summarizes
the confirmed information and extracts and classifies explicit requirements.
The developer reviews the proposals at each stage and can return to and edit
earlier stages. From the approved requirements, IDE3.0 generates Java
interfaces with JML contracts that the coding assistant must implement.

IDE3.0 has four components, each covered by its own functional tests:
\begin{itemize}
  \item \textbf{Refinement workflow.} Guides the developer from a
  natural-language goal through decomposition (impact-mapping), clarification, and
  specification to proposed requirements and constraints (FR1--FR3).
  \item \textbf{Review panel and approval gate.} The developer approves,
  edits, or rejects each proposal in VS Code. Code generation is blocked
  until every proposal has a recorded decision (FR4--FR8).
  \item \textbf{Intent model store.} Persists approved artifacts, their
  rationale, and their trace links in the \texttt{.ide3/} folder of the
  developer's workspace (FR9, FR11).
  \item \textbf{Verification arm.} Generates Java interfaces with JML
  contracts from approved requirements and checks the coding assistant's
  implementation against them using OpenJML (FR10, FR13).

\end{itemize}

The primary objective to be accomplished via this plan is to build confidence
that the IDE3.0 extension correctly carries the developer's intent from a very
high overview of a goal down to verified code generation without loss,
fabrication, or friction. The plan aims to validate the following:

\begin{enumerate}
\item \textbf{Pipeline correctness.} Each elicitation stage produces output that fits and adheres to the shape of the defined intent model schema, and the complete context (original goal, intermediate artifacts, user corrections, confirmed constraints, and unresolved questions) is passed between stages.
\item \textbf{No silent invention.} When a goal or a user story leaves something unspecified, the clarification stage asks the developer for guidance and context rather than inserting an assumption into the requirements.
\item \textbf{Approval gate enforcement.} No artifacts should enter the intent model, nor should any code generation occur, without explicit approval from the human in the loop (and it should be recorded).
\item \textbf{Traceability integrity.} Every approved generated requirement links back to the origination of the goal, user story, and clarification answers, and editing earlier stages correctly ripples through and identifies the affected artifacts downstream.
\item \textbf{Persistence.} The intent model survives across all sessions.
\item \textbf{Contract verification.} Generated JML contracts are well-formed, and OpenJML detects implementations that violate them.
\end{enumerate}

The quality of generated requirements is additionally reviewed against the
characteristics of well-formed requirements in IEEE/ISO/IEC 29148.

\subsection{Verification and Validation Plan Verification}

% \wss{The verification and validation plan is an artifact that should also be
% verified.  Techniques for this include review and mutation testing.}

% \wss{The review will include reviews by your classmates}

The VnV plan is a project artifact that must itself be verified for
completeness, feasibility, and effectiveness. It will be verified
through team, supervisor, and peer reviews, a feasibility assessment,
mutation testing, and validation of the rubric used to evaluate
LLM-generated artifacts.

\paragraph{Team Review.}
All team members will review the plan using the checklist, confirming that
each objective in Section 2.2 is covered by at least one test and that each
test case is executed as written. The plan will also be checked for
consistency with the SRS and design documents, including component names,
requirement numbers, and tools.

\paragraph{Supervisor Review.}
Dr.\ David will review the test plan for the elicitation pipeline and the
verification arm. We will ask whether the planned tests would give the
developers confidence, or whether there are any crucial testing gaps that
need to be addressed. We will further ask him: Would the failures and the
successes give a more than adequate guarantee that the components function
as they are intended to?

\paragraph{Peer Review.}
There will be a peer review of our plan that is dictated by this document lifecycle, and the issues and recommendations for changes in our approach will be documented on GitHub under Issues.

\paragraph{Feasibility Assessment.}
The technical verification co-leads will confirm that every planned activity is realistic within the project timeline and the team's current skills, time budget, and ability to overcome a not so steep learning curve (if it comes down to it). Activities that cannot be completed in time will be rescoped or listed as out of scope, rather than left unexecuted.

\paragraph{Mutation Testing.}
To verify that the planned tests can detect defects, there will be an intentional introduction of faults injected into the implementation to see if the test cases fail. Any fault that no test detects shows there is a gap in the plan, and a test case will be added to cover it.

\paragraph{Evaluation Rubric Validation.}
The quality of the LLM-generated artifacts will be evaluated against an evaluation (eval) suite. We will manually score a set of deliberately flawed outputs (such as requirements having invented constraints or missing trace links) and confirm that each one falls below the pass threshold. If any of the flawed outputs are considered acceptable, then the evals and acceptance rubric would need to be revised. When the LLM-as-judge is used, its scores will be compared with our manual ratings on a sample of acceptable outputs.

\paragraph{Tracking and Success Metrics.}
All findings will be logged in GitHub Issues and addressed in our team meetings, so that the plan can be refined and retuned. Progress can be measured via requirement coverage, mutation detection rate, and finally issue resolution rate.

Implementation verification ensures that the source code that is implemented successfully satisfies a valid implementation and satisfies the requirements that are outlined in the SRS. 
It should combine dynamic testing and static testing. 

\paragraph{System and Unit Tests.} 
All functional and non-functional requirements shall be verified through the system test plans in Section 4 and Section 5, and the unit test cases in Section 6. Each test should trace to at least one requirement, and there should be full requirement coverage. 

\paragraph{Evaluation Suite}
Due to the nature of LLM-generated artifacts being non-deterministic, other than the expected output schema, the elicitation pipeline will be verified via an eval suite created by the team. 
The suite will be rerun whenever a prompt, model, or pipeline stage changes, so that regressions in output quality are caught early. The rubric itself is validated as described in Section~3.4.
The suite will consist of fixed scenario goals, each having their own gaps that the agent should raise. The pipeline's output for each scenario is scored against a rubric derived from the objectives in Section 2.2 and the requirement quality that is outlined by IEEE/ISO/IEC 29148. 

\paragraph{Static Contract Verification}
In addition to checking the code during runtime, OpenJML's static checking will be used to verify the AI agentic coding assistant's Java implementation against the generated JML contracts without executing the code. 
This will allow us to test for contract violations on routes/paths that dynamic testing might not be able to pick up. 

\paragraph{Static Analysis and Linters}
The team will utilize linters for static analysis that will be integrated in the CI pipeline, and a PR will not be able to be successfully merged into the main branch from a feature branch until all the failed blocks are resolved. 

\paragraph{Peer Code Inspection.}
All code changes require review and approval through a GitHub pull request by team members other than the author (a minimum of 2 approvals is required before a merge is possible). Reviewers will
specifically check for:
\begin{itemize}
  \item Correct handling of the full context passed between elicitation
  stages.
  \item No path that allows an artifact to bypass the approval gate.
  \item Trace links being created and updated whenever artifacts change.
  \item Proper handling of malformed or unexpected LLM output.
  \item Adherence to coding standards and the module interfaces.
\end{itemize}

\paragraph{Code Walkthrough.}
The Revision~0 demonstration will be used as a code walkthrough and knowledge transfer. The team will trace one example goal through the system end-to-end, from elicitation to contract verification, and explain the code responsible for each stage. Feedback from Dr.\ David, the TA, and classmates will be tracked as GitHub Issues.

\subsubsection{Intent Capture}

This area covers submission of engineering intent, extraction of structured
engineering artifacts, and iterative refinement into reviewable proposals
and contracts, as described by FR1-FR3 in the SRS \citep{SRS}. Test
identifiers begin with \texttt{IC}, followed by a functionality group and
a case number. The groups cover engineering artifact submission
(\texttt{IC-EAS}), natural-language submission and interpretation
(\texttt{IC-NL}), iterative refinement and contract readiness
(\texttt{IC-IR}), and requirement and constraint identification
(\texttt{IC-RC}).

\paragraph{Engineering Artifact Submission}

These tests assess whether \progname{} uses the information supplied in
engineering artifacts, identifies issues or uncertainty, and seeks further
input when the artifact does not justify a sufficiently detailed contract.
UML and Petri net support are planned capabilities, and the corresponding
tests will be executed as those artifact types become supported. Comprehensive 
model verification, including Petri net deadlock analysis, is a potential 
extension beyond these cases.

All cases are manual system tests using small artifacts with independently
reviewed expected interpretations. Fixtures include the information needed
to establish each expected result. Checks compare meaning and relationships,
not exact generated wording or a particular contract language.

\begin{enumerate}

\item{IC-EAS-1: Submit a Valid UML Diagram\\}

Requirements: FR1, FR2, FR3.

Control: Manual.

Initial State: A project is open. A reviewed UML class diagram defines an
Account with a numeric balance and a withdraw(amount) operation. Attached
constraints state that the amount must be positive, must not exceed the
balance, and is subtracted from the balance on success.

Input: The engineer submits the diagram and its constraints through the
extension.

Output: A reviewable draft represents the Account, balance, operation, and all
three withdrawal rules without contradicting their supplied meanings.

Test Case Derivation: FR1 accepts supported engineering artifacts, FR2
requires structured extraction and refinement, and FR3 requires a reviewable
draft.

How test will be performed: The tester will submit the fixture and compare the
resulting draft with the reviewed diagram and constraints, checking each
specified element and rule.

\item{IC-EAS-2: Submit a Valid Petri Net\\}

Requirements: FR1, FR2, FR3.

Control: Manual.

Initial State: A project is open. A reviewed Petri net has places Ready and
Complete, a transition Process, arcs Ready to Process and Process to Complete,
and one initial token in Ready. All arc weights are one. An accompanying
description identifies a transition firing as a completed processing action.

Input: The engineer submits the net and its description.

Output: The draft captures that Process requires a token in Ready and moves
that token to Complete when it fires. It preserves the initial marking and
does not invent concurrent processing or additional transitions. The
interpretation is available for review.

Test Case Derivation: FR1 and FR2 require supported artifact input to inform
the structured proposal; FR3 requires the interpretation to be reviewable.

How test will be performed: The tester will submit the fixture and compare the
extracted behaviour with the independently reviewed token-flow interpretation.

\item{IC-EAS-3: Identify an Erroneous UML Relationship\\}

Requirements: FR1, FR2.

Control: Manual.

Initial State: A UML fixture shows Account inheriting from SavingsAccount and
SavingsAccount inheriting from Account. The fixture is reviewed in advance to
identify the circular inheritance as the seeded error.

Input: The engineer submits the diagram without resolving the inheritance
cycle.

Output: The system identifies the circular relationship and asks the engineer
to correct or clarify it. The affected relationship is not silently accepted
as confirmed intent or used as a settled basis for a contract.

Test Case Derivation: Refinement under FR2 must address an identified
inconsistency in artifact input before relying on it to derive a contract.

How test will be performed: The tester will submit the fixture, inspect the
reported issue and clarification request, and check that the affected
relationship remains unresolved in any retained draft.

\item{IC-EAS-4: Identify an Incomplete Petri-Net Definition\\}

Requirements: FR1, FR2.

Control: Manual.

Initial State: A Petri net fixture declares places Ready and Complete and
transition Process, but one arc references a place named Failed that is absent
from the supplied net and accompanying description.

Input: The engineer submits the fixture with the missing place definition.

Output: The system identifies the unresolved arc endpoint and requests its
definition or correction. It does not silently invent the missing place or
treat the net as a complete confirmed behavioural specification.

Test Case Derivation: FR2 requires refinement of supplied intent; a referenced
but undefined element must be resolved before the affected behaviour can
support a contract.

How test will be performed: The tester will submit the fixture and inspect the
refinement response and draft for identification of Failed, a request for
clarification, and absence of an invented confirmed definition.

\item{IC-EAS-5: Clarify Informal UML Notation\\}

Requirements: FR1, FR2.

Control: Manual.

Initial State: An otherwise readable UML-like diagram connects Account and
Customer using an unlabelled arrow with no legend. The accompanying
description does not establish whether it means ownership, association, or
inheritance.

Input: The engineer submits the diagram.

Output: The system identifies the uncertain relationship and asks the engineer
to confirm its meaning. It may suggest an interpretation, but does not
silently treat one as confirmed. Unambiguous information remains available for
refinement.

Test Case Derivation: FR2 requires iterative refinement where the supplied
artifact does not establish a unique interpretation.

How test will be performed: The tester will inspect the response for a
question about the relationship and verify that any proposed meaning is
clearly unconfirmed rather than incorporated as a settled requirement.

\item{IC-EAS-6: Refine an Understandable but Insufficient Artifact\\}

Requirements: FR1, FR2, FR3.

Control: Manual.

Initial State: A clear UML diagram defines Account, balance, and
withdraw(amount), but provides no rules for permitted amounts, overdrafts, or
the resulting balance.

Input: The engineer submits the diagram without additional behavioural rules.

Output: The system retains the class, attribute, and operation in a draft and
asks for the missing withdrawal rules before completing a contract that
depends on them. It does not silently assume that amounts must be positive,
overdrafts are forbidden, or a particular balance update applies.

Test Case Derivation: FR2 requires iterative refinement toward detailed
contracts, while FR3 allows the known information to remain available as a
draft. A readable artifact may still lack the necessary behavioural detail.

How test will be performed: The tester will submit the diagram, inspect the
captured structural details and clarification questions, and check that
missing rules are not presented as confirmed contract conditions.

\item{IC-EAS-7: Incorporate Clarification of an Artifact\\}

Requirements: FR2, FR3.

Control: Manual.

Initial State: The diagram in IC-EAS-5 is pending clarification of the
Account--Customer relationship.

Input: The engineer states that the relationship is an association: each
Account belongs to exactly one Customer, and a Customer may have zero or more
Accounts. It does not represent inheritance.

Output: The revised draft captures the association and stated multiplicities,
excludes inheritance as the confirmed interpretation, and remains available
for review. Previously captured compatible artifact information is preserved.

Test Case Derivation: FR2 requires the engineer's clarification to guide
refinement; FR3 requires the resulting draft to be available for review.

How test will be performed: The tester will reproduce the pending
clarification, submit the answer, and compare the revised relationship and
multiplicities with the supplied explanation.

\item{IC-EAS-8: Derive a Contract After Supplying Missing Detail\\}

Requirements: FR2, FR3.

Control: Manual.

Initial State: The Account diagram in IC-EAS-6 has been interpreted, and
withdrawal rules remain unresolved.

Input: The engineer specifies that the withdrawal amount must be positive and
no greater than the current balance, and that a successful withdrawal reduces
the balance by that amount.

Output: A contract proposal includes both amount restrictions and the stated
balance update, consistently tied to the withdraw operation. It remains
pending engineer review and does not retain the supplied rules as unresolved
or introduce a contradictory overdraft policy.

Test Case Derivation: FR2 requires refinement into more detailed contracts
using the engineer's information. FR3 requires the resulting proposal to be
available for review.

How test will be performed: The tester will reproduce the incomplete-artifact
state, supply the missing rules, complete any further necessary clarification,
and inspect the proposed contract for the two preconditions, balance update,
and pending review status.

\end{enumerate}

\paragraph{Natural-Language Submission and Interpretation}

These tests cover requests that start at different levels of detail. The
tester checks that the system uses what has already been provided and asks
for missing information rather than filling it in silently. Each case starts
with a separate request in an open project. These are manual tests, and
outputs are compared by meaning rather than exact wording.

\begin{enumerate}

\item{IC-NL-1: Submit a Broad System Description\\}

Requirements: FR1, FR2, FR3.

Control: Manual.

Initial State: A project is open with no proposal for the new request.

Input: ``I want a small application where users can keep track of their tasks
and mark them complete.

Output: The system captures task tracking and completion as proposed
functionality, makes the draft available for review, and asks for further
detail needed to refine it. It does not treat the broad description as a
complete basis for implementation contracts.

Test Case Derivation: FR1 accepts natural-language requests, FR2 requires
extraction and refinement, and FR3 requires a reviewable draft.

How test will be performed: The tester will submit the request and inspect the
draft and follow-up questions. Task sharing, reminders, and other unspecified
features must not appear as confirmed requirements.

\item{IC-NL-2: Submit a Partially Detailed Requirement\\}

Requirements: FR1, FR2, FR3.

Control: Manual.

Initial State: A project is open with no proposal for the new request.

Input: ``Users can withdraw money from their account, but they cannot withdraw
more than their balance.

Output: The draft preserves the withdrawal behaviour and balance restriction.
The system asks about missing rules, including permitted amounts and the
effect on the balance, before completing a contract that depends on those
rules.

Test Case Derivation: FR2 requires supplied information to be retained while
missing detail is obtained through interaction.

How test will be performed: The tester will submit the requirement and check
that the balance restriction is preserved and the missing rules are raised
rather than silently assumed.

\item{IC-NL-3: Submit a Detailed Request\\}

Requirements: FR1, FR2, FR3.

Control: Manual.

Initial State: A project is open with no proposal for the new request.

Input: ``Allow withdrawals of positive whole units only, up to 5,000 units per
withdrawal and no more than the available balance. A successful withdrawal
subtracts the amount. A rejected withdrawal leaves the balance unchanged. Do
not add other operations.

Output: The proposal preserves all supplied rules. Follow-up questions concern
remaining gaps rather than requiring the engineer to restate these rules. Once
necessary clarification and review are complete, the information can be used
to propose a contract.

Test Case Derivation: FR2 requires refinement based on the information already
supplied, regardless of how detailed the initial request is.

How test will be performed: The tester will compare the proposal and questions
with each supplied rule, respond to any remaining relevant questions, and
review the resulting proposal. Brief confirmation of supplied rules is
acceptable.

\item{IC-NL-4: Interpret Equivalent Wording\\}

Requirements: FR1, FR2.

Control: Manual.

Initial State: Two separate requests start with the same empty project
context.

Input: The first request states ``A withdrawal must not exceed the available
balance. The second states ``Users cannot take out more money than they
currently have in their account.

Output: Both proposals express the same balance restriction. Differences in
wording or organization do not introduce different withdrawal policies.

Test Case Derivation: FR2 requires extraction of the intended requirement,
which should not change solely because equivalent natural-language wording is
used.

How test will be performed: The tester will submit each request separately and
compare the extracted restriction. Any additional clarification is answered
consistently in both runs.

\end{enumerate}

\paragraph{Iterative Refinement and Contract Readiness}

These tests follow the request from an initial description through requirements
to contract proposals, supporting FR2--FR3 and PUC2 and PUC4. Before requesting
contracts, the tester reviews and approves the relevant refined engineering
artifacts as required by PUC4. Generated contracts remain proposals for review.

For \texttt{IC-IR-1}, the tester uses a reference sheet for a small account
withdrawal component. The initial prompt is ``I want a small component that
lets a user withdraw money from an account.'' The reference sheet contains:
\begin{itemize}
  \item Amounts are positive whole units.
  \item The limit is 5,000 units per withdrawal.
  \item Withdrawals cannot exceed the available balance; overdrafts are not allowed.
  \item Successful withdrawals subtract the amount from the balance.
  \item Rejected withdrawals leave the balance unchanged.
  \item Deposits, transfers, fees, and scheduled withdrawals are outside the request.
\end{itemize}
The limit and other rules are sample input, not targets for \progname{}.
The tester answers questions from this sheet when prompted, including broad
questions about limits, exceptions, and scope. The tester does not volunteer
missing rules simply to complete the expected output. Questions may occur in
any order and may cover several rules at once. If a necessary rule is not
elicited before the system treats refinement as complete, the omission is
recorded. If the interaction does not reach completion, it is recorded as
incomplete rather than passed. The tester retains the conversation and
resulting proposals as evidence.

\begin{enumerate}

\item{IC-IR-1: Refine a Broad Request Through Conversation\\}

Requirements: FR1, FR2, FR3; PUC2, PUC4.

Control: Manual.

Initial State: A new request is ready, and the tester has the account
withdrawal reference sheet above.

Input: The tester submits the broad initial prompt and answers clarification
questions using the reference sheet.

Output: The system elicits the necessary rules and produces reviewable
requirements consistent with the sheet. After approval of those requirements,
the contract proposals express the permitted amount, per-withdrawal limit,
balance restriction, and balance effects. Excluded features are not included
as confirmed functionality.

Test Case Derivation: FR2 and PUC2 describe iterative refinement; PUC4
describes deriving contracts after the relevant artifacts have been approved.

How test will be performed: The tester will follow the conversation, record
which questions elicit each rule, review the refined requirements, and approve
them when consistent with the supplied information. The tester will then
inspect the proposed contracts against every reference-sheet rule.

\item{IC-IR-2: Do Not Complete a Contract With a Missing Rule\\}

Requirements: FR2, FR3; PUC2, PUC4.

Control: Manual.

Initial State: A pending request allows account withdrawals but does not
specify whether overdrafts are permitted.

Input: The tester asks for a withdrawal contract without supplying the
overdraft policy.

Output: The system asks for the missing policy and leaves the affected
contract condition unresolved. It does not silently finalize either an
overdraft prohibition or an overdraft allowance.

Test Case Derivation: FR2 and PUC2 require clarification of insufficient
detail before PUC4 contract generation can rely on it.

How test will be performed: The tester will request the contract, withhold the
policy, and inspect the response and any draft conditions. A clearly
incomplete draft is acceptable; an assumed policy presented as settled is not.

\item{IC-IR-3: Continue After a Partial Clarification\\}

Requirements: FR2, FR3; PUC2.

Control: Manual.

Initial State: The system has asked whether withdrawal amounts must be
positive and whether overdrafts are allowed.

Input: The engineer answers only ``The withdrawal amount must be positive.

Output: The positive-amount rule is retained, and the system continues seeking
the overdraft policy before completing the affected contract. It does not
treat the partial answer as resolving both questions.

Test Case Derivation: FR2 and PUC2 require refinement to continue where
necessary information remains missing.

How test will be performed: The tester will establish the two missing rules,
provide only the positive-amount answer, and check the updated draft and
subsequent clarification.

\item{IC-IR-4: Preserve Earlier Rules During Refinement\\}

Requirements: FR2, FR3; PUC2.

Control: Manual.

Initial State: A draft already records positive whole-unit withdrawals and a
5,000-unit per-withdrawal limit.

Input: In later clarification, the engineer prohibits overdrafts and specifies
that rejected withdrawals leave the balance unchanged.

Output: The updated draft contains both earlier rules and both newly supplied
rules without changing their meanings. None of the earlier rules disappears
when later detail is added.

Test Case Derivation: FR2 requires iterative refinement of the accumulated
intent, and FR3 requires the updated draft to remain reviewable.

How test will be performed: The tester will supply the rules in separate
exchanges and compare the final draft with the information given at each step.

\item{IC-IR-5: Derive Conditions From Refined Requirements\\}

Requirements: FR2, FR3; PUC4.

Control: Manual.

Initial State: Reviewed and approved requirements specify positive whole-unit
withdrawals, a 5,000-unit per-withdrawal limit, no overdrafts, subtraction on
success, and no balance change on rejection. The starting balance is
nonnegative.

Input: The engineer requests implementation contracts for the withdrawal
operation.

Output: The contract proposal expresses all amount restrictions and both
balance outcomes, and preserves a nonnegative balance. It is associated with
the relevant requirements and available for review. The conditions do not
permit behaviour prohibited by the approved requirements.

Test Case Derivation: PUC4 requires precise contracts derived from approved
artifacts, including preconditions, postconditions, or invariants as
appropriate.

How test will be performed: The tester will inspect the contract conditions
against the approved rules. The representation may use preconditions or
explicit rejection cases, but must describe both successful and rejected
withdrawals consistently. Exact syntax or a particular contract language is
not required.

\item{IC-IR-6: Exclude Unrequested and Declined Features\\}

Requirements: FR2, FR3; PUC2, PUC4.

Control: Manual.

Initial State: A withdrawal-only component is being refined. Deposits,
transfers, fees, and scheduled withdrawals are explicitly outside scope.

Input: The engineer completes clarification for withdrawals and declines any
suggestions to add the excluded features.

Output: The resulting requirements and contract proposals remain limited to
withdrawals. Excluded features are not retained as confirmed requirements or
contract obligations.

Test Case Derivation: FR2 requires refinement of the engineer's intent, rather
than expansion into functionality the engineer has excluded.

How test will be performed: The tester will follow the withdrawal refinement
flow, state the scope exclusions, and inspect the resulting requirements and
contracts for unwanted features. Recording exclusions or declined suggestions
as context is acceptable.

\end{enumerate}

\paragraph{Requirement and Constraint Identification}

These tests check the types of information extracted under FR2, not the
performance or quality of a generated application. Quality targets and
technology choices in the input are example requirements supplied by the
tester. They do not set targets or implementation choices for \progname{}.
A quality requirement may also be represented as a quality constraint;
the check is that its meaning and role are preserved. Constraints that do
not map directly to operation contracts must remain represented in the
engineering artifacts rather than being dropped.

\begin{enumerate}

\item{IC-RC-1: Identify Separate Functional Requirements\\}

Requirements: FR1, FR2, FR3.

Control: Manual.

Initial State: A new natural-language request is ready for submission.

Input: ``Users can create tasks, rename an existing task, and mark a task
complete. Only the selected task should change when it is renamed or
completed.

Output: The draft identifies creation, renaming, and completion as distinct
behaviours and preserves the selected-task restriction for the relevant
operations.

Test Case Derivation: FR2 requires extraction of structured functional
requirements while retaining the conditions attached to each behaviour.

How test will be performed: The tester will submit the request and inspect the
draft for all three behaviours and the restriction on which task may change.

\item{IC-RC-2: Identify a Quality Requirement\\}

Requirements: FR1, FR2, FR3.

Control: Manual.

Initial State: A task-management request is pending, with task listing already
identified as functionality.

Input: ``The task list must be usable with a keyboard without requiring a
mouse.

Output: The draft retains keyboard accessibility as a quality requirement or
constraint applying to task listing, rather than replacing it with unrelated
functionality.

Test Case Derivation: FR2 explicitly includes nonfunctional requirements and
quality constraints in the extracted artifacts.

How test will be performed: The tester will submit the accessibility need and
inspect its representation and association with the task-list functionality.

\item{IC-RC-3: Clarify a Vague Quality Statement\\}

Requirements: FR1, FR2, FR3; PUC2.

Control: Manual.

Initial State: A request includes a task search function but no response-time
target or workload conditions.

Input: ``Task searches should respond quickly.

expectation and relevant conditions. It does not silently assign a numerical
response-time target.

Test Case Derivation: FR2 and PUC2 require refinement of insufficiently

How test will be performed: The tester will submit the statement and inspect

\item{IC-RC-4: Identify a Mandated Design Constraint\\}

Requirements: FR1, FR2, FR3.

Test Case Derivation: FR2 requires design constraints to be extracted from the

How test will be performed: The tester will submit the constraint and inspect

\item{IC-RC-5: Extract a Mixed Request\\}

Control: Manual.

Initial State: A new request is ready with no existing proposal.

Input: ``Users must be able to create and complete tasks. They must be able to
do both using only a keyboard. Task data must be stored in SQLite to work with
our existing database.

Output: The draft captures task creation and completion, keyboard
accessibility for both actions, and the mandated SQLite constraint. The
quality and design constraints remain associated with the relevant
functionality without being lost during refinement.

Test Case Derivation: FR2 requires functional requirements, nonfunctional
requirements, quality constraints, and design constraints to be represented
together where supplied.

How test will be performed: The tester will submit the mixed request, answer
relevant clarification questions, and check the resulting draft for each
behaviour and constraint and their intended scope.

\end{enumerate}

\subsubsection{Requirement Review and Approval}

This area tests the presentation, approval, rejection, and revision of
engineering proposals required by FR4-FR6 in the SRS \citep{SRS}.
Related checks cover draft availability (FR3), iterative refinement (FR2),
recorded review decisions (FR8), and persistence of approved intent (FR9).
Test identifiers use \texttt{RRA}, a group code, and a case number:
\texttt{PR} for presentation, \texttt{AD} for accept/decline,
\texttt{ED} for editing through refinement, and \texttt{PA} for pending item
amendment and removal. Accept and decline correspond to approve and reject
in the SRS.

All cases are manual system tests performed through the extension's review
workflow. Each case uses a separate proposal unless stated otherwise.
Persistence checks reopen the same project in a new session and retrieve
its recorded artifacts and decisions, without assuming a storage location
or mechanism. Rejected proposals may be retained as history, but must not
be recorded as approved intent. For generated revisions, the tester checks
the specified meaning rather than exact wording. Report related requirements
below are sample input to \progname{}, not requirements for \progname{} itself.

\paragraph{Presentation}

\begin{enumerate}

able to export reports and the constraint ``Exports shall use CSV format.

Input: The engineer opens the proposal for review.

Output: Both items are available for inspection with their complete content
and pending review status. Neither is presented as approved.

Test Case Derivation: FR4 requires requirements and quality constraints to be
presented for review; FR3 requires the draft to be available.

How test will be performed: The tester will open the prepared proposal and
compare the displayed items and review status with the known draft content.

\item{RRA-PR-2: Present an Implementation Contract\\}

greater than zero, amount no greater than the current balance, and a resulting
balance equal to the previous balance minus the amount.

for inspection. The contract is identified as pending review.

Test Case Derivation: FR4 requires contracts to be presented before
corresponding code generation. The engineer must be able to inspect the
proposed conditions.

How test will be performed: The tester will compare the displayed contract

\subsubsection{Intent Model, Rationale, and Traceability}

These tests check the record that remains after approval: the artifacts,
why they exist, and which code and tests realize them. They correspond to
FR9 and FR11, and to PUC7 and PUC8.

\paragraph{Persistence and Traceability}

\begin{enumerate}

\item{IM-1: Record Approved Artifacts\\}

Requirements: FR9.

Control: Automated.

Initial State: A proposal for the fixture has been approved, and the
\texttt{.ide3/} store is empty.

Input: The approval of that proposal.

Output: The store contains the approved requirements, quality constraints,
and design rationale. The files validate against the intent-model schema.
Each artifact records its identifier and its links to related artifacts.
Reopening the workspace shows the same record.

Test Case Derivation: FR9 requires a versioned intent model with a
structured schema, holding the approved requirements, constraints, and
rationale. Reopening checks that the record belongs to the project rather
than to one session.

How test will be performed: The tester will approve the proposal, validate
the written files against the schema, reload the extension host, and read
the model again.

\item{IM-2: Trace a Requirement to Code and Tests\\}

Requirements: FR9, PUC7.

Control: Manual.

Initial State: One approved requirement has an accepted implementation and
an accepted test, and the trace links between them are recorded.

Input: The developer selects that requirement and asks for its
implementation trace.

Output: The view lists the implementing source and the test, and it shows
the requirement those files are linked to. A requirement with no
implementation yet shows an empty trace rather than a link to an unrelated
file.

Test Case Derivation: FR9 requires traceability from intent-model elements
to the code and tests that implement and satisfy them. PUC7 is this query.

How test will be performed: The tester will select the linked requirement
and an unlinked requirement, and compare the listed files with the links
stored in \texttt{.ide3/}.

\item{IM-3: Explain Why an Implementation Exists\\}

Requirements: FR11, PUC8.

Control: Manual.

Initial State: The state produced by IM-2.

Input: The developer selects the implementation linked to that requirement
and asks why it exists.

Output: The view shows the originating request, the approved requirement,
and the recorded rationale. The rationale is the text stored at approval
time.

Test Case Derivation: FR11 requires, for each approved requirement and
design decision, the rationale and the originating request. PUC8 is the
query from an implementation artifact back to that record.

How test will be performed: The tester will select the implementation, open
the intent explanation, and match the request text, requirement identifier,
and rationale to the intent model.

\end{enumerate}

\subsubsection{Verification of Generated Changes}

These tests check the verification arm. Approved constraints become checks
the generated code must meet, and a change that breaks them is reported.
They correspond to FR10 and FR12. The contract form for the capstone
demonstration is a Java interface annotated with JML, checked with OpenJML.
The project reuses that checker rather than building one.

\paragraph{Verification}

\begin{enumerate}

\item{VF-1: Report Whether a Change Satisfies the Intent Model\\}

Requirements: FR10.

Control: Automated.

Initial State: The approved model contains one precondition and one
postcondition. The expected interpretation names both, and names the
requirement each comes from.

Input: Two implementations of the same behaviour. One satisfies both
constraints. The other violates the precondition.

Output: The first implementation is reported as satisfying the recorded
constraints. The second is reported as violating the precondition. The
report names that constraint and the requirement it comes from.

Test Case Derivation: FR10 requires generated changes to be checked against
the intent model, with a report of whether they satisfy the recorded
requirements and constraints.

How test will be performed: The tester will submit both versions through
the verification command and compare the report with the constraints in
the intent model.

\item{VF-2: Compile Constraints into Executable Tests\\}

Requirements: FR12.

Control: Automated.

Initial State: One precondition and one postcondition are approved. The
fixture names an input that satisfies each and an input that violates each.

Input: The approved constraint set.

Output: Executable tests are written for the approved constraints. Each
test fails on the violating input and passes on the satisfying input. Each
test is linked to the constraint it encodes.

Test Case Derivation: FR12 requires the approved requirements and quality
constraints to be compiled into executable tests that the generated code
must satisfy.

How test will be performed: The tester will generate the tests, run them
against a stub that passes and a stub that violates each constraint, and
check the trace links back to the constraints.

\item{VF-3: Check a Contract with OpenJML\\}

Requirements: FR10, PUC4.

Control: Automated.

Initial State: An approved requirement is ready for a contract. The
expected interpretation names its precondition and postcondition.

Input: A generated interface whose operation carries those two constraints
in JML. The contract is shown for review before use. A second
implementation violates the postcondition.

Output: The contract is linked to the requirement and is not used for
generation until the developer approves it. After approval, OpenJML reports
the violating implementation and the extension surfaces that report. A
satisfying implementation produces no violation.

Test Case Derivation: PUC4 requires contracts, including preconditions and
postconditions, derived from approved artifacts, linked to those artifacts,
and reviewed before implementation. FR10 requires the resulting check to be
reported.

How test will be performed: The tester will generate the interface, confirm
the review gate holds, approve the contract, run OpenJML on both
implementations, and match the extension's report to OpenJML's output.

\end{enumerate}
