\section{Introduction}

This document presents the hazard analysis for \progname{}, an IDE-integrated
tool that captures engineering intent from AI-assisted development, maintains a
versioned intent model with traceability to code and tests, and verifies
AI-proposed changes against that model before they take effect.

The following definitions are adapted from the STPA Handbook
(Leveson and Thomas, 2018):

\begin{itemize}
  \item \textbf{Loss:} Something of value to stakeholders that is unacceptable
  to lose. Losses may include loss of mission, loss of reputation, loss or leak
  of sensitive information, or other stakeholder-unacceptable outcomes.
  \item \textbf{Hazard:} A system state or set of conditions that, together with
  a particular set of worst-case environmental conditions, will lead to a loss.
  \item \textbf{System:} A set of components that act together to achieve a
  common goal. A system may contain subsystems and may be part of a larger
  system.
\end{itemize}

In this software setting, a hazard is a state or condition of \progname{} (or of
its interaction with the IDE, AI coding assistant, network, or workspace) that
can lead to failure, unintended behaviour, loss of engineering control, or
other unacceptable outcomes. The analysis identifies such hazards early and
records strategies to eliminate or mitigate them.

\paragraph{Requirement identifiers.}
In this document, labels \textbf{SR1}--\textbf{SR12} refer to
\textit{safety and security requirements derived from the FMEA}
(Section~\ref{sec:SR}). Citations of SRS requirements use the Volere prefixes
(FR, SCR, ACR, IR, IMR, EUR, and so on). Where the SRS reuses a prefix
(for example Safety-Critical \textbf{SCR1} versus Standards Compliance
\textbf{SCR1}), the citation names the SRS subsection.

\section{Scope and Purpose of Hazard Analysis}

The purpose of this hazard analysis is to identify hazards that may arise when
using \progname{}, analyze their causes and effects, and define mitigations.
Completing the analysis early produces safety and security requirements that
can be reflected in the SRS and design before implementation locks in unsafe
behaviour.

The losses of concern for \progname{} include:
\begin{itemize}
  \item Loss of engineering intent (requirements, constraints, and rationale
  become incomplete, incorrect, or unrecoverable).
  \item Loss of human control over AI-generated changes (code is produced or
  merged without explicit developer approval).
  \item Loss of traceability between intent and implementation (links to code
  and tests become missing, stale, or unjustified).
  \item Incorrect acceptance decisions (the system reports that a change
  satisfies the intent model when it does not, or vice versa).
  \item Leakage of private project content (source code, requirements, or
  design rationale exposed through external LLM or logging services).
  \item Loss of developer trust or wasted effort (false confidence in the
  intent model, unclear workflow, or repeated failed verification cycles).
  \item Legal or license exposure from AI-generated content that incorporates
  third-party material without appropriate rights or attribution.
\end{itemize}

Physical harm is not in scope for this tool. Security, privacy, data integrity,
usability-driven misuse, AI over-trust, compliance, and software-quality harms
are in scope.

\section{System Boundaries and Components}

\progname{} runs locally as an IDE extension coordinated with an AI coding
assistant, with optional calls to external LLM services and Git-backed
versioning of the intent model. The system is divided into the following
major components for hazard brainstorming (not a full design):

\begin{enumerate}
  \item \textbf{Intent Capture / Requirement Extraction}: accepts
  natural-language requests and extracts structured draft requirements,
  quality constraints, and design constraints (SRS FR1 to FR3).
  \item \textbf{Requirement Review and Approval}: presents proposals for
  approve, edit, or reject before code generation (SRS FR4 to FR6, G5).
  \item \textbf{Code Generation Control}: gates the AI coding assistant so
  implementation proceeds only after an approved decision (SRS FR7 to FR8,
  IAS2, Safety-Critical SCR1).
  \item \textbf{Intent Model Store}: persists the versioned structured
  intent model (requirements, constraints, rationale) (SRS FR9, FR11, G2,
  IR1 to IR4, REL2).
  \item \textbf{Traceability}: maintains justified links from intent
  elements to code and tests (SRS FR9, G3, EUR3).
  \item \textbf{Change Verification}: checks AI-proposed or generated
  changes against the intent model and reports the results (SRS FR10, FR12, G4,
  AUR3).
  \item \textbf{IDE Extension / User Interface}: VS Code / Cursor (and
  related) surfaces for review, status, and developer interaction
  (SRS AR1 to AR2, EUR1 to EUR2, IAS1).
  \item \textbf{External LLM / Network Services}: the LLM service that the
  LangGraph workflow calls for extraction and verification, and LangSmith
  tracing (SRS Off-the-Shelf Software, IMR1 to IMR2, PRR1).
  \item \textbf{Version Control Integration}: Git / GitHub versioning of the
  intent model alongside the project (SRS IAS3, ACR2 to ACR3).
\end{enumerate}

\section{Critical Assumptions}

The following assumptions bound the analysis. Assumptions that would hide
important failure modes are avoided where possible.

\begin{itemize}
  \item The developer using \progname{} is authorized to work on the local
  project and is not intentionally sabotaging the intent model
  (consistent with SRS ACR1 for a single local workspace owner).
  \item The host IDE and operating system provide a writable project workspace.
  \item An AI coding assistant that supports the product's MCP integration
  surface (SRS IAS2) is available when gated generation is used.
  \item Network connectivity may fail; hazards from offline or failed LLM
  calls are retained in the FMEA.
  \item Git is available when intent-model versioning features are used; local
  persistence hazards are still analyzed if Git is unavailable.
  \item The developer can read and act on UI feedback in the host IDE
  (SRS EUR1 to EUR2).
\end{itemize}

\section{Safety and Security Requirements}
\label{sec:SR}

The following requirements were identified through the FMEA. Several are already
stated in the Volere SRS; those are listed under \textit{Related SRS}. 
\newline
\noindent\textbf{SR1.} The system shall require an explicit developer approve,
edit, or reject decision on every extracted proposal before the proposal can
update the intent model or authorize code generation.\\
\textit{Rationale:} Incorrect extraction must not silently become approved
intent.\\
\textit{Associated hazards:} H1-1, H2-1\\
\textit{Related SRS:} FR3 to FR6, Safety-Critical SCR1, EUR2, G1, G5

\medskip
\noindent\textbf{SR2.} The system shall present proposals in a clear, structured
form and shall make the actions available at each review step explicit.\\
\textit{Rationale:} Unclear UI causes wrong or skipped approvals.\\
\textit{Associated hazards:} H2-1\\
\textit{Related SRS:} EUR1, EUR2, UPR1, FR4

\medskip
\noindent\textbf{SR3.} The system shall show, for each extracted requirement,
the part of the developer's request it came from, or flag items with no such
source.\\
\textit{Rationale:} Injected or ungrounded requirements must be visible to the
reviewer.\\
\textit{Associated hazards:} H1-1\\
\textit{Related SRS:} FR4, FR11

\medskip
\noindent\textbf{SR4.} The system shall notify the developer when capture,
review, verification, or IDE sync fails or is degraded, and shall provide
status when a long-running operation begins.\\
\textit{Rationale:} Silent failure encourages bypass of the tool.\\
\textit{Associated hazards:} H1-2, H2-1, H7-1, H8-1\\
\textit{Related SRS:} PR2, IMR2, Supportability SR1

\medskip
\noindent\textbf{SR5.} The system shall allow interrupted draft proposals to be
resumed or safely discarded without losing already-approved intent.\\
\textit{Rationale:} Lost drafts push developers to skip the review workflow.\\
\textit{Associated hazards:} H2-1\\
\textit{Related SRS:} RFR1, RFR3, FR3, FR5 to FR6

\medskip
\noindent\textbf{SR6.} The system shall prevent the AI coding assistant from
implementing a request until a human decision is recorded, and shall keep
generation blocked on timeout or lost connection.\\
\textit{Rationale:} The approval gate must hold when integration fails.\\
\textit{Associated hazards:} H3-1\\
\textit{Related SRS:} FR7 to FR8, IMR2, Safety-Critical SCR1

\medskip
\noindent\textbf{SR7.} The system shall accept approve, edit, and reject
decisions only from the developer through the IDE panel, and shall not expose
them as tools the AI coding assistant can call.\\
\textit{Rationale:} Self-approval by the assistant defeats human control.\\
\textit{Associated hazards:} H3-1\\
\textit{Related SRS:} ACR1, IAS2, G5

\medskip
\noindent\textbf{SR8.} The system shall ensure that a developer decision either
updates the intent model and is communicated to the AI coding assistant
completely, or leaves both unchanged and reports failure.\\
\textit{Rationale:} Partial updates desynchronize the gate and the source of
truth.\\
\textit{Associated hazards:} H3-1\\
\textit{Related SRS:} FR8, IR1

\medskip
\noindent\textbf{SR9.} The system shall reject schema-invalid intent-model
writes, record decision outcomes and times, retain recoverable version history
(including Git-compatible storage and uncommitted-change warnings), and preserve
compatibility across releases or provide migration.\\
\textit{Rationale:} Corrupt, untracked, or unreadable intent destroys the
mission of the tool.\\
\textit{Associated hazards:} H4-1, H9-1\\
\textit{Related SRS:} IR2 to IR4, AUR1, AUR2, FR9, FR11, IAS3, REL2, ACR2,
Standards SCR3, RFR2

\medskip
\noindent\textbf{SR10.} The system shall detect and report missing, broken, or
unjustified traceability links between intent-model elements and associated
code or tests.\\
\textit{Rationale:} Traceability is required to explain AI-generated structure.\\
\textit{Associated hazards:} H5-1\\
\textit{Related SRS:} FR9, FR11, EUR3, G3

\medskip
\noindent\textbf{SR11.} The system shall verify AI-proposed or generated changes
against the latest approved intent model, present evidence of what was checked,
never treat infrastructure failure as a pass, and state that behaviour outside
the checked requirements was not verified.\\
\textit{Rationale:} False passes and bare pass labels create over-trust.\\
\textit{Associated hazards:} H6-1\\
\textit{Related SRS:} FR10, FR12, AUR3, IMR2, G4

\medskip
\noindent\textbf{SR12.} The system shall minimize project content sent to
external LLM or tracing services, shall not send secret or Git-ignored files
such as \texttt{.env}, shall document what may leave the machine, and shall
allow the developer to disable tracing.\\
\textit{Rationale:} Leakage of private code or requirements is a stakeholder
loss.\\
\textit{Associated hazards:} H8-1\\
\textit{Related SRS:} PRR1

\section{Roadmap}

Not all safety and security requirements can be fully implemented within the
capstone timeline. Priority for Revision~0 / Proof of Concept follows the
primary risk: a trustworthy intent-to-implementation mapping under human
approval.

\begin{itemize}
  \item \textbf{In scope for the capstone timeline (Rev~0 / PoC focus):}
  SR1, SR6, SR7, SR8, SR9, SR11, together with SRS FR3 to FR10,
  Safety-Critical SCR1, ACR1, IR1 to IR4, and IMR1 to IMR2.
  \item \textbf{Targeted for later / stretch within the course:}
  SR2, SR3, SR4, SR5, SR10 (clearer review UX, source flags, degraded-mode
  polish, draft recovery, and trace-break detection).
  \item \textbf{Likely future work beyond the course if not reached:}
  SR12 (egress minimization and privacy controls for external LLM and
  LangSmith traffic).
\end{itemize}

\section{Appendix --- Reflection}

\input{../Reflection.text}

\begin{enumerate}
    \item What went well while writing this deliverable?

    Analyzing one component at a time made the FMEA systematic. For each
    component we asked what happens if it fails, if its output is wrong, or if
    a dependency is unavailable. Giving each hazard an ID and each mitigation
    an SR number made traceability simple.

    Several hazards were already covered by existing requirements. The
    approval gate (FR4 to FR8) was written to keep the developer in control
    (G5), and it is also the main mitigation for H1-1, H2-1, and H3-1.

    \item What pain points did you experience during this deliverable, and how
    did you resolve them?

    The SRS and the hazard analysis were written at the same time on separate
    branches. The first draft of the FMEA was written before the SRS security
    and robustness sections existed, so it did not reference them. During
    review we checked every cited ID against the SRS, linked each SR to the
    matching SRS requirements, and added hazards the SRS pointed to, such as
    the AI assistant approving its own proposal (ACR1).

    It was not obvious what counts as a hazard for a tool with no risk of
    physical harm. Using the STPA definition of a loss (Section~1) resolved
    this. Losing engineering intent, losing control over AI changes, and
    leaking private code are all losses.

    Most of the writing happened in the two days before the deadline. For the
    V\&V Plan, we will start earlier to leave time for review.

    \item Which of your listed risks had your team thought of before this
    deliverable, and which did you think of while doing this deliverable? For
    the latter ones (ones you thought of while doing the Hazard Analysis), how
    did they come about?

    \textbf{Known before.} The Development Plan names our primary risk:
    keeping an accurate, synchronized model of how code maps to intent. This
    appears as H4-1, H5-1, and H6-1. The Problem Statement names AI code
    drifting from its specification, which appears as H3-1.

    \textbf{New during this deliverable.}
    \begin{itemize}
      \item \textit{AI self-approval and prompt injection (H1-3, H3-3).}
      Reviewing the SRS access requirement ACR1 and the planned MCP design
      showed that the assistant itself could approve a proposal, or be told to
      by text in the workspace.
      \item \textit{Rubber-stamp approvals (H2-1).} Treating the developer as
      part of the system showed that an approval gate only works if the
      developer actually reviews.
      \item \textit{Partial decision recording (H3-2).} Asking what happens if
      a decision reaches the intent model but not the AI assistant showed the
      two can fall out of sync.
      \item \textit{Silent pass on checker failure (H6-2).} Asking what the
      checker reports when it crashes showed a crash could be read as a pass.
      \item \textit{Code and secrets leaking to external services (H8-1).}
      Listing what the system sends over the network showed that source code,
      requirements, and API keys may reach the LLM provider or LangSmith.
      \item \textit{LLM cost (H8-3).} The SRS budget constraint states the
      project has no budget, so a retry loop against a paid API is a real
      loss.
      \item \textit{Offline operation and Git divergence (H1-2, H8-2, H9-1).}
      These came from asking what happens when the network or version control
      is unavailable.
    \end{itemize}

    \item Other than the risk of physical harm (some projects may not have any
    appreciable risks of this form), list at least 2 other types of risk in
    software products. Why are they important to consider?

    \begin{itemize}
      \item \textbf{Security and privacy.} Data the software handles is
      accessed or disclosed without permission. This matters because leaked
      data cannot be recalled and can have legal consequences. For
      \progname{}, this is code sent to external LLMs (H8-1).
      \item \textbf{Data integrity.} Stored data becomes wrong or corrupted
      without anyone noticing. This matters because later decisions build on
      that data. For \progname{}, a corrupted intent model (H4-1) would make
      every later verification unreliable.
      \item \textbf{Over-reliance.} Users trust the software more than they
      should. This matters because the harm occurs even when the software
      works as designed. For \progname{}, a ``verified'' label could lead
      developers to stop reviewing AI code (H6-1), which is why SR11 requires
      stating what was not verified.
    \end{itemize}
\end{enumerate}
