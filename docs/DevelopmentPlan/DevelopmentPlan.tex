GitHub will be used to manage the project workflow, with GitHub Projects serving as the team’s Kanban board for tracking tasks, issues, and project progress.
Each significant task, feature or bug will be represented by a GitHub issue. Each issue will  contain a description and the relevant acceptance criteria. Issues will be assigned to team members and moved through the project board as work progresses.
Development will be done on a branch based workflow. A separate branch will be created for each issue. Changes will be committed regularly and pushed to the shared repository.
Once an issue is complete, a pull request will be opened to merge to the main branch. Pull requests will explain the changes made, reference the related issue, and identify any testing or verification performed. At least one other team member will review the pull request before it is merged. Review feedback must be addressed before approval.
We will employ github actions for various code quality and testing procedures including automated tests, linting, formatting, and other validation checks. Documentation will be updated within the same issue or pull request to keep the repository documentation up to date.
The main branch will represent the current stable state of the project. Direct changes to the main branch will be avoided, with project work entering through reviewed pull requests. 

\end{itemize}

\section{Project Decomposition and Scheduling}

We are using GitHub Projects as our Kanban board to decompose and track work.
Each deliverable (Problem Statement, Development Plan, SRS, Design Document,
etc.) is broken down into GitHub issues representing concrete tasks, such as a
specific section to write or a specific module to implement. Issues are
labelled by deliverable and by type (documentation, implementation, testing),
assigned to a team member, and moved across the board (Todo, In Progress, In
Review, Done) as work progresses. This gives the team a single view of what is
outstanding for the current deliverable and who owns each piece.

Link to our GitHub project: \url{https://github.com/users/RishabShine/projects/4}

At a high level, the project is scheduled around the sequence of deliverables
set by the course: Problem Statement and Development Plan, followed by the
Software Requirements Specification and Hazard Analysis, the Verification and
Validation Plan, the Proof of Concept demonstration, the Design Document, the
Complementary Documents, Module Implementation, the Rev 0 demonstration, the
VnV Report, and finally the Final Demonstration, Final Documentation, and
EXPO. Each deliverable has an associated peer review period immediately
following its due date.

Within each deliverable window, the team decomposes the work into issues at
the start of the window, produces a rough draft by the midpoint, holds an
internal team review before the deadline, and reserves the final period
before submission for addressing feedback and formatting. This buffer
accounts for peer review turnaround and keeps the team from finishing work
right at the deadline.

\section{Proof of Concept Demonstration Plan}

The primary risk to the success of our project is whether we are able to construct and maintain a model that accurately represents the relationships between a software system’s implementation and engineering intent.

Our tool is dependent on understanding how files, classes, code, and other artifacts relate or map to requirements, constraints, and design decisions. We must be able to justify each of these relationships and update each of these relationships as code is added or updated, and new features are added. This functionality is required before we can focus on higher level, user facing functionality, such as constraint aware code generation, design rational tracking, etc.

The main challenges in demonstrating this representation will be determining how these relationships can be identified accurately, how these relationships can be justified, and how the model can remain synchronized as the software project changes. A requirement, design decision, or new feature can affect multiple files, classes, and code, making these relationships difficult to identify and maintain. As the implementation evolves, previously established relationships may become outdated or invalid, requiring the model to detect and reflect these changes while preserving accurate traceability.

Therefore, for our proof of concept, we will focus on demonstrating this underlying representation, rather than showcasing a subset of features that we aim to eventually have, as this piece of functionality is the foundation for any features we will add. Given a software project and a set of requirements, constraints, and design choices, the system will construct a model that maps these to implementations. For each of these relationships, the system should be able to provide a justification of how the connection was established.

For the project the model artifact that we hope to generate is based on the input provided by the user in natural-language to an AI Assistant. The AI would also be used to generate code based on the intent model, test cases, class and code structure descriptions, explanations, and relationships with the rest of the code, and comments on PRs ( if we get to one of our stretch goals).

\begin{enumerate}
    \item Why is it important to create a development plan prior to starting the
    project?

    Creating a development plan before starting the project forces the team to
    get a deeper understanding of the project and its scope before any code is
    written, so that work is planned out instead of going in blind. It gives the
    team a concrete outline to work from and ensures everyone is on the same
    page: what is going on, what is expected of them, and what the rest of the
    project will look like. Having this plan in place also leads to fewer issues
    down the line, since decisions around workflow, quality, and team
    accountability are made up front rather than being figured out reactively.

    \item In your opinion, what are the advantages and disadvantages of using
    CI/CD?

    The main advantage is that it catches problems early. Tests, linting, and
    formatting checks run automatically on every change, so bugs and style
    issues get flagged before they are merged instead of piling up. It also
    makes it safer to merge often, since every change is checked the same way.
    For this project specifically, it fits naturally with the intent model too,
    since automated checks are basically what would let the system verify that
    AI-generated changes still satisfy the tracked requirements.

    The main disadvantage is the setup and upkeep cost. Someone has to write
    and maintain the pipeline, and if it is not configured well it can slow the
    team down or give a false sense of security if the checks do not actually
    cover what matters. Debugging a failure in CI can also be more annoying
    than just debugging locally.

    \item What disagreements did your group have in this deliverable, if any,
    and how did you resolve them?

    The group did not have any disagreements while writing this deliverable.
    If disagreements come up in future deliverables, the team will resolve them
    the way described in the Attitude section above: by discussing the issue
    together as a team, and if the team cannot reach agreement on its own,
    bringing it to the TA or instructor for guidance.
\end{enumerate}

\subsubsection*{In Case of Emergency}

% \wss{What process will team members follow if they have an emergency and cannot
% attend a team meeting or complete their individual work promised for a team
% deliverable?}

If a team member has an emergency, they will notify the team as soon as reasonably possible through the team's main communication channel. 
Where possible, they will share the status of their current work, including what is complete, what remains, and where the work is located.

A delegate will then be assigned to take over the absent member's action items for that week. If the absent member is unable to 
arrange this themselves, the remaining team members will assign a delegate at the next meeting or through the team channel. 
If the delegate is already overloaded, the team will hold a meeting to create a remediation plan and redistribute the work among available members. 

To make transfers of responsibility seamless, all members should know what everyone else is working on through the weekly meetings, 
even if not the implementation details. Because the team follows shared coding standards and keeps work in the shared repository, 
any member should be able to understand, navigate, and pick up another member's work based on prior knowledge.

\subsection*{Accountability and Teamwork}

\subsubsection*{Quality}

Team members are expected to come to meetings prepared, with any questions about the
project or their assigned work thought out in advance, and with their own work
completed to the point agreed upon at the previous meeting. Members should be ready
to discuss the status, decisions, and any blockers related to their respective roles.

All deliverables, including code and documentation, are peer reviewed through a pull
request before being merged. A pull request should only be merged once it meets the
team's quality bar: it satisfies its requirements, follows the team's coding and
documentation standards, and has been checked by at least one other team member.
Work that does not meet this standard is sent back for revision rather than merged
as-is.

\subsubsection*{Attitude}

The team adopts the
\href{https://www.contributor-covenant.org/}{Contributor Covenant Code of Conduct}
as its code of conduct, rather than writing one from scratch. All team members are
expected to interact with each other professionally, as they would in a workplace,
treating one another with courtesy and respect in meetings, pull requests, and chat.

All ideas are welcome and can be raised at any time, whether in a meeting, a group
chat, or a one-on-one conversation, and no idea is dismissed without discussion.
However, before an idea is actually implemented, it must be discussed as a team and
have the agreement of all team members. This ensures that changes to the project's
direction, design, or scope are not made unilaterally.

Disagreements are expected to be resolved through discussion at a team meeting. If
the team cannot reach agreement on its own, the disagreement will be brought to the
TA or instructor for guidance.

\subsubsection*{Stay on Track}

Work will be distributed evenly across the team, with each member assigned a
roughly equal share of issues for a given deliverable. Progress against these
issues will be tracked through the team's issue tracker and reviewed at weekly
team meetings, so that a member falling behind is caught early rather than
discovered close to a deadline.

If a team member is unable to complete their assigned work, is blocked, or
otherwise cannot meet a commitment, they are expected to relay this to the team
as soon as they become aware of it, rather than waiting until the work is due.
Once an issue is raised, the team will decide together how to redistribute the
affected work or otherwise resolve the situation.

Team members are not expected to repeatedly chase a peer about unfinished work in
the days leading up to a deadline; a single status check partway through the
deliverable is sufficient, and it is the responsibility of the assigned member to
flag problems before that point. Repeated failure to do so will be treated as
under-contribution.

The team's project management metrics (attendance, commit history, and issue
completion, as collected for the TA and instructor) will be used to identify
whether a team member is contributing their fair share. A member who is
consistently below target will first be raised directly with them by the team; if
the issue persists, the team will bring it to the TA or instructor for guidance
on how to proceed.

\subsubsection*{Team Building}

Team cohesion will be built through regular meetings, frequent communication, and collaborative development practices. Each merge request will be reviewed by at least two other team members, ensuring that everyone remains aware of the work being completed across the project, frequent contact between team members, and that team members are not working in isolation.

Higher-level design and project decisions will also be discussed as a group during team meetings.

Outside of development work, the team may also organize informal activities, such as meeting for coffee or spending time together outside scheduled project meetings, to strengthen communication and working relationships which will help enhance team cohesion.

\subsubsection*{Decision Making} 

Smaller implementation level decisions will follow the coding standards, naming conventions, and design patterns established by the team beforehand. Within these guidelines, team members will have discretion over how they implement their assigned work. Any concerns with an individual member's implementation level decisions can be raised during merge request reviews and can be raised to a team discussion which can also set future precedence.

Larger decisions that affect the overall project direction, architecture, or design will be discussed as a team during meetings prior to starting any of the implementation. The team will aim to reach a consensus, however, if not possible, the minimum expectation is that all members can understand and agree with the reasoning behind the final decision, even if their preferences differ.
